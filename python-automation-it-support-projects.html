Python Automation for IT Support: 3 Practical Scripts You Can Build Today

IT support involves plenty of small, repeated tasks: checking disk space, reviewing system logs, and finding devices that have stopped reporting. Python can turn those tasks into repeatable, testable workflows. You do not need an AI model, an expensive cloud account, or a complicated dashboard to begin.

This is a hands-on tutorial with three independent scripts. Each uses only Python's built-in modules, so you can practise on a normal laptop. The examples use local data and never connect to someone else's system.

By the end of this guide, you will have:
  • A read-only disk health report that can flag low free space.
  • A log summariser that counts repeated failed SSH login messages in a sample file.
  • An asset inventory checker that identifies inactive or outdated device records.
  • A framework for turning scripts into documented, maintainable IT tools.

1. Why IT support teams use Python

Good automation removes repetitive manual work while keeping people in control. Imagine opening the same dashboard every morning to check free storage or copying asset records into a weekly report. A small script can do those checks consistently and produce an output that a technician can review.

MonitorSystem health

Read local system information and highlight a condition that deserves attention.

InvestigateOperational logs

Identify repeated patterns in files you are authorised to examine.

OrganiseAsset inventory

Check whether device records appear incomplete, old, or inactive.

Python helps with processing and reporting. It does not replace proper monitoring, patching, backup, security controls or incident-response procedures. An automated warning should guide a technician's next check—not trigger a destructive action without review.

2. Set up your free Python workspace

Use a supported Python 3 installation from python.org. On macOS or Linux, open Terminal and create a working folder:

mkdir python-it-lab
cd python-it-lab
python3 -m venv .venv
source .venv/bin/activate
python --version

On Windows, create the environment using py -m venv .venv and activate it in PowerShell using .venv\Scripts\Activate.ps1 if permitted by the local execution policy. These projects use the standard library, so no pip install is required. Keep the sample files in the same folder as your Python scripts.

3. Project one: a disk space health report

Difficulty: Beginner / Read-only / Windows, macOS and Linux

A full disk can stop applications from saving logs, downloading updates, or writing new data. Python's shutil.disk_usage() reports space information for a filesystem containing the selected path. Let's check the filesystem where your home directory lives.

Create disk_health.py:

from datetime import datetime
from pathlib import Path
import json
import shutil

disk = shutil.disk_usage(Path.home())

used_percent = round(
    100 * (disk.total - disk.free) / disk.total, 1
)

report = {
    "checked_at": datetime.now().astimezone().isoformat(
        timespec="seconds"
    ),
    "location": "Home filesystem",
    "used_percent": used_percent,
    "free_gib": round(disk.free / (1024 ** 3), 1),
    "status": "REVIEW" if used_percent >= 85 else "OK",
}

print(json.dumps(report, indent=2))

Run it with python disk_health.py. You will see a JSON report containing a timestamp, available storage and a simple status. The 85% threshold is an example, not a universal operational standard. Real systems need thresholds based on their workloads, disk growth and alerting requirements.

Why it matters: A technician can add this kind of check to a broader health reporting workflow. The script reads disk statistics and does not remove files or change system configuration.

Important: Checking Path.home() tells you about that filesystem only. A computer may have multiple disks, mount points or containers. A status of OK is not proof that every storage device is healthy.

4. Project two: analyse failed SSH login messages

Difficulty: Beginner to intermediate / Offline log exercise

Security and IT operations often begin with logs: what happened, when did it happen and how often did it repeat? For this exercise, use a fabricated SSH log file. We will count failures by source address, not access a live server, block traffic or make claims about an intrusion.

Create sample_auth.log with the following lines. The IP addresses are documentation-only examples:

2026-11-17T09:01:00Z sshd[101]: Failed password for invalid user guest from 192.0.2.10 port 22 ssh2
2026-11-17T09:02:00Z sshd[102]: Failed password for invalid user guest from 192.0.2.10 port 22 ssh2
2026-11-17T09:03:00Z sshd[103]: Failed password for invalid user guest from 192.0.2.10 port 22 ssh2
2026-11-17T09:04:00Z sshd[104]: Failed password for test from 203.0.113.8 port 22 ssh2

Next create review_log.py:

from collections import Counter
from pathlib import Path
import re

pattern = re.compile(
    r"Failed password .*? from (\d{1,3}(?:\.\d{1,3}){3})"
)
failures = Counter()

with Path("sample_auth.log").open(
    encoding="utf-8", errors="replace"
) as log:
    for line in log:
        match = pattern.search(line)
        if match:
            failures[match.group(1)] += 1

for address, count in failures.most_common():
    if count >= 3:
        print(f"Review {address}: {count} failed logins")

Run python review_log.py. Expected output:

Review 192.0.2.10: 3 failed logins

This introduces three useful Python concepts: re for regular expressions, Counter for event counts, and line-by-line file reading to avoid loading a whole log into memory.

Production caveat: Real log formats vary, including across distributions and SSH configurations. This example pattern only covers a narrow format, does not fully validate IP addresses and makes no distinction between suspicious activity and a user typing the wrong password. A real log pipeline also needs time windows, trusted source data, permission controls and human investigation.

Security practice: Only examine logs from systems you own or are authorised to administer. Logs can contain personal or sensitive information. Do not publish production logs or automatically block an address based on this tutorial's simple counter.

5. Project three: find inactive and outdated devices

Difficulty: Beginner / CSV reporting

An IT asset spreadsheet might record device identifiers, status and the last time the device was seen. This example flags devices whose status is not active or whose last-seen date is more than 30 days old.

Create devices.csv:

asset_id,status,last_seen
LAP-001,active,2026-11-15
PC-014,active,2026-10-01
SRV-005,inactive,2026-11-16

Create check_inventory.py:

import csv
from datetime import date, timedelta

cutoff = date.today() - timedelta(days=30)

with open(
    "devices.csv", newline="", encoding="utf-8"
) as file:
    for row in csv.DictReader(file):
        asset = row.get("asset_id") or "unknown"

        try:
            last_seen = date.fromisoformat(
                row["last_seen"]
            )
        except (KeyError, TypeError, ValueError):
            print(f"Review {asset}: invalid last_seen date")
            continue

        reasons = []
        status = (row.get("status") or "").strip().lower()

        if status != "active":
            reasons.append("not active")
        if last_seen < cutoff:
            reasons.append("not seen in 30+ days")

        if reasons:
            print(f"Review {asset}: {', '.join(reasons)}")

Run python check_inventory.py. With the example's dates and a run date of November 17, 2026, the output is:

Review PC-014: not seen in 30+ days
Review SRV-005: not active

The script calculates its cutoff from the day it is run, so the results will naturally change as time passes. In an actual inventory system, you would also validate column names, handle duplicate asset IDs, define an approved retention policy and explain exactly where the last-seen timestamps come from.

6. From practice script to a reliable IT tool

Running once on your laptop is a start. A useful IT automation tool also needs predictable behaviour when things go wrong. Before scheduling or sharing any script, check these basics:

  1. Handle failures clearly. A missing file, malformed date or inaccessible path should produce an understandable error instead of a misleading result.
  2. Keep operations read-only by default. Start with reports and dry-run behaviour before attempting changes to user files or services.
  3. Use least privilege. Do not run a simple inventory report as an administrator unless an approved requirement makes elevated rights necessary.
  4. Keep credentials out of source code. Do not paste passwords, tokens or private keys into files that might reach a public repository.
  5. Test realistic edge cases. Try an empty CSV, an unexpected header, a missing log file and a small disk-volume example.
  6. Document what the script checks. A disk check is not full monitoring; three failed logins are not automatic proof of an attack.
  7. Introduce scheduling gradually. Once tests and logging work, consider Windows Task Scheduler or a supported Linux systemd timer, under your organisation's change process.

7. Build one professional portfolio project from these examples

Instead of uploading three unconnected scripts, turn them into a small IT Operations Report repository. Use a structure such as:

python-it-lab/
  README.md
  disk_health.py
  review_log.py
  check_inventory.py
  sample_auth.log
  devices.csv
  tests/

Your README should describe supported operating systems, prerequisites, sample inputs, expected outputs, limitations and how to run each tool. Add a few automated tests, include a screenshot or safe example report and clearly state that your sample data is fabricated.

For a useful next step, separate data reading from business logic, then write a unit test for the 30-day inventory rule. If a project eventually sends notifications, make alerts opt-in, implement reasonable rate limits and prevent sensitive information from leaking into messages.

8. Where artificial intelligence fits—and where it does not

None of the three projects needs AI. They are valuable because they produce reliable, understandable results from well-defined rules. AI becomes an option when a task involves ambiguity—for example, grouping support-ticket descriptions or summarising large volumes of authorised troubleshooting notes. Even then, use human review and carefully protect confidential information.

If you are beginning with Python, build the deterministic version first. Once you can explain the inputs, outputs and tests, you can evaluate whether an AI component offers enough benefit to justify its additional cost and complexity.

Final takeaway

Learn Python by solving specific operational problems. A disk report, an offline log summary and a clean asset check teach more than copying a complicated automation project you cannot debug. Start with safe sample data, write readable code, validate the output and document its limitations. Those habits scale from an entry-level IT script to a well-maintained automation workflow.
