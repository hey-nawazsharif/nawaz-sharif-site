What Is a Server? Types, Hardware, Setup From Scratch and How AI Uses Servers

What exactly makes a computer a server? What hardware is inside? How do you build one, install the operating system, connect it to a network, secure it and serve something useful? And what changes when you move from a home lab to a small office, a real-estate company, a large corporation, a government organisation or an AI data centre? This guide starts at zero and explains each layer.

Short answer: A server is a computer or software service that provides resources to other devices (called clients), usually over a network. It may be a repurposed PC, a mini PC, a tower or rack server, a virtual machine, a cloud instance or a cluster. The server is defined by its job, not a mandatory special-looking metal box.

1. What is a server? Hardware versus service

Imagine your laptop asking a website for a page. The browser is the client. Somewhere, web-server software processes the request and sends back HTML, images or data. The software might run on a physical machine or inside a virtual machine. Either can be a server.

There are two overlapping meanings of the word: server hardware (a computer built or configured for service workloads) and a server role (software offering a networked function such as web hosting, database access or file sharing). A desktop can become a server when it provides a service; a dedicated server can run multiple roles at once.

Unlike a personal computer, many production servers are designed for 24/7 operation, remote administration, fault detection, serviceability, larger RAM capacity and sometimes redundant power and storage. None of those features alone is what makes the system a server.

2. Client–server computing: the simplest explanation

  1. A client discovers an address or hostname for the service through local configuration or DNS.
  2. The client connects over a network such as Ethernet, Wi-Fi or the Internet.
  3. Server software listens on an appropriate network port, applies permissions and processes the request.
  4. It might read files or query a database and return the result.
  5. Administrators monitor uptime, log failures, deploy updates and restore service when something goes wrong.

For example, a browser requests a site over HTTPS (usually TCP port 443). A Windows laptop might access a protected office file share using SMB, or an administrator might connect over SSH. Ports and protocols describe the service, not the server's physical size.

8. How is a physical server assembled?

For a ready-made enterprise server, follow the vendor's manual and do not dismantle components unnecessarily. If you are assembling a compatible home-lab computer, the process is broadly similar to PC building.

  1. Validate compatibility.

    Check CPU socket and platform, supported memory type, board power connectors, PSU wattage, chassis size, heatsink clearance, drive interfaces and BIOS support.

  2. Prepare a safe workspace.

    Unplug equipment, use sensible electrostatic-discharge precautions and keep drinks and loose metal parts away. Never open a power supply or work on live electrical components.

  3. Install compatible CPU and cooling.

    Use the exact socket instructions, retention mechanism, compatible thermal solution and vendor-recommended torque where specified.

  4. Install RAM in approved slots.

    Use the board's population guide; RDIMM and consumer UDIMM are not universally interchangeable. Check required minimum and matched-memory rules.

  5. Mount board, drives and optional PCIe cards.

    Secure the motherboard, SSDs/HDDs, NIC or GPU (if needed) without blocking airflow.

  6. Connect power and fans.

    Attach only supported internal connectors; verify heatsink fans, airflow direction and PSU input specifications.

  7. Connect network and initial console.

    Use Ethernet, keyboard and display, or a secure remote console if the server provides one. A UPS is valuable for important systems.

  8. First boot: check firmware and diagnostics.

    Enter BIOS/UEFI or vendor setup, verify CPU/RAM/disks, configure correct boot mode, update firmware from trusted vendor instructions and run hardware diagnostics.

Rack installations: heavy equipment, rails, power circuits and high-airflow requirements can create physical hazards. Follow site and vendor safety rules; use qualified rack/power specialists where needed. Dell provides a dedicated installation and iDRAC setup guide.

9. From zero: install Ubuntu Server and connect it to your LAN

Let's turn a spare PC into a local-only Linux web server. This guide follows the broad process in Canonical's official Ubuntu Server installation tutorial. Installer screens vary by release and hardware, so use the vendor guide if they differ.

  1. Plan the machine and service.

    Choose a spare device, a test-only SSD, a wired LAN and a short hostname such as homelab-server. Write down which disk may be erased and which computers will access it.

  2. Download a supported Ubuntu Server LTS ISO.

    Use ubuntu.com/download/server. Select the correct CPU architecture, verify the published checksum and use a trusted USB imaging tool such as Ubuntu's documented procedure. Do not use the OS installer on a computer with unbacked-up personal data.

  3. Create bootable USB and start the installer.

    Insert the USB, connect monitor/keyboard, open the firmware boot menu (key varies by vendor), select the USB and start Ubuntu Server installation.

  4. Confirm language, keyboard and networking.

    Use the detected wired connection initially, often via router DHCP. You can reserve the address in the router later instead of guessing a static IP during installation.

  5. Choose storage carefully.

    Select only the intended test disk. The “use entire disk” option erases selected partitions and existing data. For production, review encryption, filesystem, RAID, capacity and recovery design before continuing.

  6. Create a named admin user.

    Set the hostname, non-default username and a strong unique passphrase. Keep installation credentials in a secure password manager. Install OpenSSH only if remote shell access is part of the lab.

  7. Finish and restart.

    Remove the USB if prompted, boot into the installed OS, log in locally and confirm that the LAN interface has an IP address.

  8. Run first health checks.

    Use the commands below and record your actual hostname, IP, disk capacity and OS version. Do not assume the IP addresses in examples match your network.

hostnamectl
ip -br address
ip route
lsblk -f
df -h
free -h
sudo apt update
sudo apt upgrade

Expected checks: hostnamectl shows the system identity; ip -br address lists network interfaces; lsblk -f displays block devices and filesystems; df -h shows mounted capacity; free -h reports system memory. Review changes before approving a major package upgrade.

10. Install your first working web server (local lab)

Now add a simple service using NGINX. These commands assume Ubuntu Server, that your user may run sudo, that package repositories are reachable and that your server remains on a trusted private LAN.

Step A — Install and verify the service locally

sudo apt install nginx
sudo systemctl enable --now nginx
sudo systemctl status nginx --no-pager
curl -I http://127.0.0.1

Success: the service is running and the local HTTP request returns a successful response. The default page is a demonstration, not a production application.

Step B — Identify your LAN subnet before changing firewall rules

ip -br address
ip route
sudo ufw status verbose

For a sample private subnet of 192.168.1.0/24 only, the following commands allow SSH (port 22) and HTTP (port 80) from that LAN while denying other unsolicited inbound traffic. Replace the example subnet with your real trusted LAN; if the address differs, copying these rules unchanged may block access.

# Run at a local physical console on a trusted test server.
# Replace 192.168.1.0/24 with your actual trusted LAN subnet.
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 192.168.1.0/24 to any port 22 proto tcp
sudo ufw allow from 192.168.1.0/24 to any port 80 proto tcp
sudo ufw enable
sudo ufw status numbered
Remote-lockout warning: If managing the server remotely, make sure a matching SSH allow rule exists before enabling or changing the firewall; have console recovery access available. Do not open the web or SSH ports on your home router to the Internet just for this exercise. Ubuntu documents UFW firewall configuration.

Step C — Connect from another computer on the same trusted LAN

Open a browser on another device and visit http://YOUR_SERVER_LAN_IP. If you enabled SSH, create a key on the client first and configure its public key on the server as explained by the official Ubuntu SSH guide. Test a second SSH session before disabling password authentication.

# On your personal client computer (not on the server):
ssh-keygen -t ed25519 -C "my-homelab-key"
# Replace the sample user and IP with your actual values:
ssh YOUR_USERNAME@YOUR_SERVER_LAN_IP

After verifying an SSH key-based login and recovery access, an administrator can tighten password and root-login policies. Keep BMC management and any hypervisor web interface on a separate trusted management network where possible.

11. What must be secured before real business use?

  • Least privilege: named individual accounts and only required administrative permissions; no shared admin password.
  • Updates and inventory: supported OS releases, tested security updates, firmware lifecycle, hardware inventory and records of changes.
  • Network separation: firewalls, restricted admin interfaces, VLANs where appropriate and private management access.
  • Strong access: SSH public keys or enterprise identity controls, MFA where supported, carefully scoped VPN or approved access gateway for remote work.
  • Secure data: encryption where justified, file permissions, retention rules, application access reviews and audit logs.
  • Backups: independent copies, protected/offline/offsite backup storage, a documented recovery process and periodic restore tests.
  • Monitoring: CPU temperature, SSD health, failed login attempts, disk utilisation, service availability, UPS status and backup alerts.
  • Disaster recovery: decide what should return first, acceptable downtime and acceptable data-loss window.
RAID is not a backup. RAID 1 can tolerate failure of one mirrored disk in a normal two-disk array, but will not recover files deleted by mistake, maliciously encrypted data or damage to the whole site. The CISA StopRansomware guidance recommends offline, encrypted backups and regular restoration testing.

12. Dedicated hardware, virtual machines or cloud: which should you learn?

A hypervisor lets one physical host run multiple isolated virtual machines. Each VM can have its own server OS, virtual CPU cores, memory and virtual disks. Hypervisors themselves need management access, backups and software updates.

Proxmox VE is an open-source virtualisation platform using KVM virtual machines and LXC containers, documented by Proxmox. A beginner can also install Ubuntu Server inside an existing local VM instead of erasing a real disk. Virtual networking must be set up carefully; keep an experimental lab isolated from business systems.

Windows Server is another common enterprise choice, especially for identity and Windows-based application roles. Microsoft's installation documentation describes Server Core and Desktop Experience; commercial licensing varies by edition and usage. Cloud VMs add a provider billing and shared-responsibility model; the cloud provider maintains physical facilities, while customers remain responsible for the security of their OS, data and applications under the chosen service model.

13. What does an ordinary server have to do with AI?

Not every server runs AI. A basic file server may use only a CPU, modest DDR5 RAM and SSDs. Modern AI infrastructure can use the same basic server concepts plus much larger computing resources and accelerators.

A typical large AI installation has GPU nodes for training and inference, CPU and management nodes for orchestration, fast shared storage for datasets and checkpoints, high-bandwidth interconnects between GPUs, and substantial cooling and power infrastructure. For example, NVIDIA's DGX B200 reference system includes eight B200 GPUs and 1,440 GB total GPU memory distributed across those GPUs. It is an AI-oriented server, not an architectural requirement for every AI application.

Small AI models can run on a laptop or mini server; large distributed model training often needs racks of accelerator servers. Learn more in how AI uses CPUs and GPUs, AI server RAM and SSD and AI infrastructure electricity and water.

14. A few simple server-sizing calculations

Think in terms of workloads and measured headroom. These are illustrations, not hardware purchasing recommendations.

Example A — CPU and RAM capacity for a small app

Suppose a test web application needs 2 GB RAM, a database needs 4 GB, and the OS and background tools need 2 GB. Initial estimated active RAM = 8 GB. Add capacity for file caching, spikes, growth and virtualization overhead before selecting real hardware. Actual values come from measuring application usage, not universal rules.

Working RAM estimate: application RAM + database RAM + OS/background RAM + safety headroom. Do not treat the example as a fixed formula for all companies.

Example B — Disk mirroring

Two 1 TB disks in a conventional RAID 1 mirror provide about 1 TB raw logical capacity, before metadata and filesystem overhead, rather than 2 TB of usable independent storage. This helps tolerate a drive failure but does not replace backups.

Example C — Energy cost

If a server actually draws an average of 120 W at the wall continuously for 30 days, then:

Energy (kWh) = Watts / 1000 × hours
             = 120 / 1000 × (24 × 30)
             = 86.4 kWh

Multiply by your real electricity tariff to estimate the energy portion of the bill. That excludes other equipment such as the router, switch, air conditioning and UPS losses unless their draw was included in your measurement. Measured average watts are different from a PSU's maximum rated watts.

15. Common beginner mistakes

  • Buying an expensive rack server before defining the application or evaluating a cheaper VM/cloud alternative.
  • Assuming a RAID array automatically protects against ransomware or accidental deletion.
  • Using an incorrect memory module or CPU/socket combination when assembling a custom machine.
  • Erasing the wrong disk in the installer without a backup.
  • Opening router ports to the public Internet for a basic local training lab.
  • Changing UFW or SSH settings remotely without testing new access first.
  • Ignoring UPS runtime, heat, noise, drive health and long-term updates.
  • Confusing rack/tower form factors with web/AI/database software roles.
  • Assuming an organisation's server must be installed inside its own office rather than with an approved provider.
  • Running production customer or government data on a learning machine without applicable security, legal or organisational controls.

Frequently asked questions

Is a server different from a normal computer?

Server hardware may provide more reliability, remote management and expandability, but a normal computer can act as a server when it runs a service for other clients.

Can I create a server without buying hardware?

Yes. You can use an existing computer to run a virtual machine. Many local VM tools let you practise Ubuntu Server without modifying your main operating system.

Does a home server need a rack and UPS?

Not necessarily. A home lab can be a mini PC on a ventilated shelf. A UPS is useful for protecting important services from outages and enabling controlled shutdowns, but the design depends on risk and availability needs.

How many server types exist?

There is no universal count because hardware types, software roles and deployment environments overlap. Common forms include mini, tower, rack, modular, GPU, storage, virtual, cloud and edge.

Does an AI server need GPU memory rather than DDR5?

Many large AI workloads use GPU-attached HBM, while host CPUs also use DDR5 or other system RAM. Smaller models can run on CPUs; GPU hardware is not a strict requirement for every AI service.

Which server should a real-estate office buy?

It depends on workload, staff count, privacy requirements, existing cloud applications, support and backup needs. A managed CRM and shared storage may be more appropriate than buying and administering a physical server.

Can a government department use any server?

No universal hardware category applies. Agencies must follow their jurisdiction's procurement, data-handling, security and service-availability requirements. Hardware selection follows those obligations.
